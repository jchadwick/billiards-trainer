# System Health prototype → API mapping and gaps

Reference: `/Users/jchadwick/Downloads/index.html`, component `DH`. The page consumes explicit HTTP liveness/readiness snapshots, the existing state WebSocket, one shared browser video receiver, and the versioned pushed diagnostics WebSocket. There is no interval HTTP polling.

| Prototype data or action | Existing source / implementation | Gap or limitation |
| --- | --- | --- |
| Server liveness | GET `/api/v1/health/live`, `{status: "alive"}` | This establishes gateway responsiveness, not camera/perception health. A failed request is Unknown rather than evidence the server crashed. |
| Server readiness | GET `/api/v1/health/ready`, `status`, `localization_available`, `freshness`, optional error/message | 503 is a real not-ready response, displayed separately from network failures. This remains an explicit checked snapshot; the separate diagnostics stream reports runtime stages. |
| Last checked / Refresh health / detail | Browser completion time; explicit GETs; expandable original responses | No polling; inspected details show the actual health response. |
| Video availability / independent preview branch | App-owned video receiver status shared across Live Diagnostics, Health, Events, and Configuration | Identified frame delivery and native image load are distinct. Native load does not establish ongoing freshness; camera-source health remains unavailable. No extra camera request is started for Health. |
| State delivery | RootStore shared WebSocket `system.status.isConnected`; receipt counter on valid `state` envelopes | Connected is still labeled connection evidence. Received-state rate is measured from existing socket receipts, before ordering rejection; it does not imply producer or camera FPS. |
| Backend stage assessments | Full snapshots from `/api/v1/diagnostics/ws`, schema v1; gateway revision increases within a gateway instance | Seven backend stages are displayed independently: gateway service, source lifecycle, capture progress, model initialization, scheduled perception work, scene delivery, localization. Missing or expired evidence is unknown/stale; the UI does not infer failure from browser silence. |
| Gateway stage / build | `gateway` identity, revision, uptime and build in the pushed diagnostics snapshot | Actual gateway package/version and optional Git revision/dirty status; unavailable provenance remains unknown. |
| Camera source lifecycle | `source_lifecycle` stage from supervisor/source lifecycle evidence | Applies to the supervised producer's reported capture source. An external/legacy producer without diagnostics stays unknown; browser video reception is a separate branch. |
| Capture progress | `capture_progress` stage, capture lifecycle and last decoded-frame progress age | Shows actual progress age where reported, not a fabricated camera timestamp or FPS. |
| Model initialization / active model | `model_initialization` stage and fresh producer metadata from a successfully initialized runtime | Active identity comes from the loaded runtime, including artifact hash/classes/dimensions/provider evidence. Loading/failure clears active identity; retained last-known metadata is labeled inactive with its age. |
| Scheduled perception work | `scheduled_perception_work`: scheduler state, active job kind, in-flight start age/deadline, expected/completed/failed jobs and last failure evidence | Deadline applies only to actual in-flight work. Phase-gated/idle/results-ready states are not reported as stalls. These ages/counters are not completed-job duration histograms or frame-drop counts. |
| Scene delivery and localization | `scene_delivery` and `localization` stage assessments from producer/scene evidence | Distinct from browser state-WebSocket connectivity and observation freshness. No prototype state IDs or timestamps are invented. |
| Browser preview / state delivery | Shared receiver and existing state-WebSocket client status | Browser-observed delivery is displayed separately from backend stages. Native image load does not establish continuing freshness, and no additional camera request is started. |
| Trend time-range controls 1m/5m/15m | Active selectors over the browser's retained one-second samples | The selected window filters the current browser session's bounded samples; it is not server history. Pre-start, disconnected, suspended and producer-replacement intervals are gaps. |
| Received state rate | Browser count of valid `state` messages from the existing state WebSocket, divided by the actual observed duration in a rolling 10-second window | Repeated and out-of-order state messages are included because this measures delivery receipts. It is browser-observed message rate, not source or camera FPS. No illustrative prototype value is rendered. |
| Observation-age trend | API-reported ball, cue and motion evidence ages sampled locally once per second and advanced from monotonic browser time | Each evidence age is tracked independently. A repeat cannot make evidence younger; only a changed evidence/source-frame identity resets age. Missing, disconnected, suspended and producer-replacement periods remain gaps. No historical API or fake samples are used. |
| Distinct observed source frames | Accepted, distinct engine/session/frame identities observed through the state WebSocket; shown separately from message rate | Phase-only updates and repeated identities do not count. Missing frame identity makes this rate unknown. It is a browser-observed state-frame rate, not producer/camera FPS or a dropped-frame counter. No illustrative `6.2 frames/s` value is rendered. |
| Perception processing time | Prototype `Not available`, `No backend timing instrumentation` highlighted | The diagnostics snapshot reports active-job age/deadline and completion/failure ages, but no measured completed processing durations, distributions, or per-stage timing history. |
| Dropped / replaced / skipped frames | Prototype `Not available`, `Counters not exposed by backend` highlighted | Scheduler job counters are exposed, but frame drop/replace/skip counters and time-window metadata are not. A scene sequence gap is not proof of a camera drop. |
| Camera-to-display latency | Prototype `Not available`, `Requires synchronized end-to-end timestamps` highlighted | No matching synchronized camera/display timing contract; measurement age is not end-to-end latency. |
| CPU, Memory, GPU | Prototype `Not available`, `No metric endpoint · window unavailable` highlighted | No resource metrics endpoint or pushed metric stream, aggregation window, retained history. Missing values are never zero. |
| Runtime active configuration / producer / session / layout / calibration / rectification | Latest state observation identity/status/perception revisions | Actual identifiers replace fixture strings; absent identifiers stay Not available. |
| Model identity / runtime version | Fresh producer metadata includes model identity and producer build; gateway build is in the same snapshot | Supported current/last-known fields are no longer highlighted. Last-known values are explicitly inactive and age-labeled. |
| Backend metric retention | Prototype `Not available · proposed integration` highlighted | The stream is latest-value and has no retained monitoring-history contract. |
| Copy runtime metadata | Browser clipboard of current diagnostics, actual state metadata and independent channel status; JSON and failure feedback | Contains no prototype producer/session/revision values; source and freshness are preserved. |

Prototype-only pipeline times (`14:32:18.408 EDT`, `14:32:18.492 EDT`, `Last activity 14:32:06 EDT`) are deliberately omitted rather than presented as live. The existing API does not supply those exact stage timestamps. Original illustrative trend chart samples are not redrawn as telemetry. Unsupported values that remain on the page carry `.highlight-issue`.

## Remaining work for full prototype behavior (not implemented)

- Server-retained cross-session history would require a new contract. Current-session message/source-frame rates and evidence-age charts are sampled locally from WebSocket receipts and API ages, retained in bounded browser memory, and lost on reload.
- Instrumented completed processing durations, per-stage frame drop/replace/skip counters, and synchronized end-to-end latency evidence.
- CPU/memory/GPU telemetry, metric windows, and history-retention metadata.
- Per-ball observation ages in the live push contract. `GET /api/v1/game/state` exposes `balls[].last_update`, but the UI does not poll it.
